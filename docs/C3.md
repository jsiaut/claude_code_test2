# Remarque sur C3 (1er novembre) : vérifications, plan et résultats

Les sections 1 à 3 ont été poussées avant les mesures ; la section 4 vient après.

## 1. La remarque

En résumé (texte reçu le 1er novembre) :

* **Verdict** : la 5e place de C3 est justifiée et robuste ; quatre notes de la matrice et deux phrases du README sont
  fausses ou périmées. C3 n'a jamais été relu (ni parmi les dix langages revus, ni parmi les huit du juge à l'aveugle).
* **Vérifié par l'auteur** : sources de c3-lang.org, billets de 0.7.0 à 0.8.5, notes de 0.8.6 sur master ; sources de
  0.8.5_1 (dernière version stable, 13 octobre) ; rejeu de l'analyse v3 (même graine, 20 000 variantes) qui retrouve le
  publié : 70,3 points, 5e, devant Rust dans 53 % des variantes.
* **Ce qui est juste** : A6 = 0, C5 = 0, D3 = 0 et D4 = 0 en lecture stricte, D5 = 0,5, E3 et E4 = 1, F4 v2 = 1 ;
  implémentation compétente, conforme à la règle « bibliothèque standard seule », versions optimisées au niveau du C
  (0,93 à 1,04 fois son temps sur K1 SoA, K6, K7, K8 tuned et K9 tuned) ; le « Banc de sympathie mécanique » classe
  aussi C3 5e.
* **Errata proposés** : C4 0 → 0,5 (`--fp-math=relaxed|fast`, -O4 et -O5 : option globale, comme Ada ; pas de contrôle
  local) ; E2 1 → 0,5 (« work in progress », environ 400 mnémoniques x86, ni chargement vectoriel, ni FMA, ni `pause`,
  ni barrière ; `asm("…")` sans opérandes) ; E5 1 → 0,5 (`@noalias` expérimental depuis 0.6.2, aucun test, et
  `llvm_codegen.c` l. 1245 pose `noalias` sur l'indice 1 en dur ; sans effet sur une tranche) ; F4 v1 0,5 → 1
  (`std::io::file::mmap`, portable POSIX et Win32 depuis 0.7.5, comme l'erratum de Zig). Textes : `@unchecked` n'existe
  pas (E6 tient par `.ptr[i]`), les builtins `$$` ne sont pas des intrinsèques de la cible (C2), `Slice2d` (F1).
  D3 et D4 seraient défendables à 0,5 (`posix::sysconf` sans la constante ; `@syscall` sans constante d'affinité, comme
  l'appel système brut de Go en v1) : jugement.
* **Effet** (analyse rejouée) : errata 70,7 points, rang espéré 6,09, 5e ; avec D3 et D4 71,8 points, 5,37, 5e ; avec
  en plus K5 et K9 mt au niveau du C (hypothèse) 71,8 points ; rang plausible 2 à 10.
* **Trois pistes à mesurer** : K5 tuned à 1,10 fois le C (`.sum()` = réduction ordonnée ; une réduction en arbre par
  `swizzle` vaudrait 1,1 point de plafond) ; K9 mt à 1,40 fois le C alors que K9 tuned fait 0,93 (depuis 0.8.0,
  `NativeThread.create` attend que le fils ait démarré, ce qui sérialise les 16 lancements de chaque répétition ;
  accessoirement, accès 512 bits désalignés dans `k9_rows`) ; le -O3 de C3 prend le pipeline O2 de LLVM (O3 seulement
  avec -O4, -O5 ou `--optlevel=max`).
* **Écarts du code par défaut, légitimes mais sans cause dans le README** : K8 naturel 1,54 fois le C (interface
  `Allocator` résolue par `.dyn_search` à chaque appel, `alloc::new` remet à zéro) ; Q1 naturel 1,30 fois (pas de TBAA :
  les pointeurs des colonnes sont relus après chaque écriture) ; K7 naturel 4,3 fois le meilleur (`HashMap` chaînée,
  une `Entry` allouée par insertion).
* **Phrases du README** : « il lui manque … le contrôle de la réassociation flottante » (c'est le contrôle local qui
  manque) ; « génériques par modules » (par déclaration depuis 0.7.9) ; K8 : le p99,9 de 277 µs est bien le plus long
  des langages classés sans ramasse-miettes, mais le maximum de 2,2 ms ne se distingue pas (Odin 2,18, Mojo 2,05).
* **Non exécuté par l'auteur** (compilateur refusé par son environnement) : `noalias` sur le mauvais paramètre, somme
  ordonnée de `.sum()`, démarrage synchrone des threads.

## 2. Vérifications (faites avant le plan)

Machine 13 (`results/hw/machine13/`) : Emerald Rapids, 4 vCPU, 2,73 à 2,77 GHz effectifs, latence à 4 Mio 36 ns, DRAM
14,8 Go/s. Chaîne : C3 0.8.5_1 (LLVM 23.1.5), compilé depuis ses sources (`/opt/src/c3c`, commit `d1b1e44`, la version
mesurée). Toutes les preuves : `tools/c3_check/collect.sh` → `results/c3_check/*.txt` (sondes dans
`tools/c3_check/probes/`). Je n'ai consulté ni le site ni master : seulement les sources et les notes de version de la
version mesurée, plus des sondes de compilation.

* **Rejeu du publié** : exact. 70,3 points, contrôle 73,1, rang espéré 6,47, 5e, devant Rust dans 53 % des variantes
  (Zig devant C3 dans 69 %), rang plausible 2 à 10.
* **Relecture** : exact. C3 n'est ni parmi les dix langages relus après coup, ni parmi les huit du juge à l'aveugle (C,
  C++, C#, D, Nim, Odin, Rust, Zig : `results/blind_notation.json`). Le « Banc » le classe bien 5e
  (`analysis/banc_data.py`).
* **Rapports aux temps du C** (données principales) : exacts. K1 SoA 0,95, Q6 tuned 0,93, Q1 tuned 1,04, K7 tuned 1,04,
  K8 tuned 0,93, K9 tuned 0,93 ; K6 mt Q6 0,90 et mt Q1 0,92 sont un peu sous la fourchette citée ; K5 tuned 1,10 ; K9
  mt 1,40 ; K8 naturel 1,54 ; Q1 naturel 1,30 ; K7 naturel 4,27 fois le meilleur (Zig).
* **C4** (`fpmath.txt`) : **exact**. `--fp-math=relaxed|fast` existe (`c3c --help`), -O4 et -O5 relâchent les
  flottants ; avec `--fp-math=relaxed`, la somme naturelle est vectorisée avec `reassoc`, et `.sum()` devient
  `reassoc`. En mode strict, `.sum()` reste `llvm.vector.reduce.fadd` sans drapeau (réduction ordonnée). Aucun
  attribut ne règle les flottants localement. La grille donne 0,5 à une option globale seule (Ada, règles v1 et v2).
  **Erratum : C4 = 0,5.**
* **E2** (`asm.txt`) : **exact sur le fond, chiffre faux**. Le jeu x86 reconnu par les blocs `asm` compte
  **217 mnémoniques** (pas environ 400) : quelques additions vectorielles (`addps`, `vaddps`…), mais ni chargement ni
  rangement vectoriel, ni FMA, ni `pause`, ni barrière (les sondes `vmovaps`, `vfmadd231ps`, `pause` et `mfence`
  échouent : « Unknown instruction for the current target »). `asm("…")` passe le texte tel quel, sans opérandes
  (`asm("pause")` compile). La mention « work in progress » de la documentation n'est pas vérifiée ici. Un sous-ensemble
  vaut 0,5 (« partielle … sous-ensemble » en v2, « limitée » en v1). **Erratum : E2 = 0,5.**
* **E5** (`noalias.txt`) : **exact, et confirmé par l'IR**. `llvm_codegen.c` l. 1245 pose `noalias` sur l'indice 1 ;
  dans la sonde, annoter le 2e paramètre marque le 1er, et une tranche annotée ne reçoit aucun attribut. Les notes de
  version de 0.6.2 disent « Add experimental `@noalias` attribute » ; aucun test ni la bibliothèque standard ne
  l'utilisent. Expérimental et défectueux : 0,5 sous les deux règles. **Erratum : E5 = 0,5.**
* **F4, règle v1** (`mmap.txt`) : **exact**. `std::io::file::mmap` (`mmap_open`, `FileMmap.bytes()`) existe depuis
  0.7.5 (notes de version), avec une version POSIX et une version Win32 de `mmap_file` ; la sonde projette
  `k1_perm.u32` et relit son premier mot sans copie. C'est le motif de l'erratum de Zig (API portable de la
  bibliothèque standard = 1 en v1). **Erratum : F4 (v1) = 1** ; v2 reste 1, texte mis à jour.
* **E6** (`unchecked.txt`) : **exact**. `@unchecked` n'est pas un attribut (« This is not a known valid attribute
  name ») ; la note 1 tient par `.ptr[i]` (indexation de pointeur sans vérification), comme pour D. Texte corrigé.
* **C2** (`c2.txt`) : **exact**. Les builtins `$$` sont des opérations génériques de LLVM (`$$fma`, `$$reduce_*`,
  `$$swizzle`, `$$masked_load`…), aucune propre à x86. La note 0,5 tient autrement : un `extern fn …
  @cname("llvm.x86…")` non documenté atteint certaines intrinsèques de LLVM (la sonde émet `pause`, mais `pext` reste un
  appel non résolu). Non documenté et partiel : 0,5. Texte corrigé.
* **F1** (`generics_slice2d.txt`) : `Slice2d` (vue 2D de la bibliothèque standard) existe ; mention ajoutée, note
  inchangée (0,5 : pas de tableau multidimensionnel dynamique natif).
* **D4** (`syscall_sysconf.txt`) : **erratum, que la remarque range en jugement**. La macro `@syscall` est publique
  (`@builtin` de `std::core::builtin`) ; la bibliothèque standard ne fournit ni `sched_setaffinity` ni la constante
  `SYS_SCHED_SETAFFINITY` (seule `SYS_GETTID` existe). La grille compte l'appel système brut : Go (règle v1, 0,5) et
  Odin (v1, 0,5). La note 0 (« aucune ») est donc fausse au regard de la grille. Sans constante ni enveloppe, c'est une
  forme partielle : **D4 = 0,5 sous les deux règles** (Go et Odin ont 1 en v2 parce que leurs paquets livrent la
  constante ou l'appel).
* **D3** : **pas d'erratum**. D3 compte une constante ou un type de bourrage ; `posix::sysconf` existe, sans la
  constante `_SC_LEVEL1_DCACHE_LINESIZE`, et une requête à l'exécution n'est comptée nulle part comme aide de
  disposition (Python, qui a `os.sysconf` avec la constante nommée, a 0). D3 = 0,5 reste une sensibilité.
* **D5, E3, E4, A6, C5** : non contestés ; D5 confirmé (`thread::fence`, pas de `pause` dans la bibliothèque
  standard ; `asm("pause")` relève de E2).
* **E7 et README, génériques** (`generics_slice2d.txt`) : **exact**. 0.7.9 : « Generics using ad-hoc `<...>` rather
  than module based » et « Module-based generics using {} is deprecated » ; 0.8.0 retire la syntaxe par module. Textes
  corrigés (README et E7) ; note inchangée.
* **K5 tuned** (`k5_reduction.txt`) : **exact**. La réduction finale de C3 est une chaîne de 16 `vaddss` dans l'ordre.
  Mais ce n'est pas un écart à une convention : dans la classe de C3 (C1 = 1), Zig et D finissent aussi par une
  réduction ordonnée (15 et 16 `vaddss`), alors que C, C++, Nim et Mojo font un arbre. La forme en arbre est une
  optimisation nouvelle (sensibilité).
* **K9 mt** (`threads.txt`) : **exact dans le source**. Sous Linux, `NativeThread.create` fait `sem_wait` jusqu'à ce que
  le fils ait relevé son identifiant (`@syscall(SYS_GETTID)`) et posté le sémaphore : les quatre lancements de chaque
  balayage sont en série. Le K9 mt de C3 suit la convention de C (quatre balayages, quatre fils créés à chaque
  balayage) : le coût vient de la bibliothèque standard, il est mesuré à bon droit. Lancer les fils par
  `posix::pthread_create` est une optimisation nouvelle (sensibilité), comme l'alignement des accès de `k9_rows`.
* **Pipeline** (`options.txt`) : **exact**. -O3 règle `OPTIMIZATION_MORE`, que `llvm_codegen.c` traduit en O2 de LLVM ;
  -O4 et -O5 donnent O3 avec des flottants relâchés ; `--optlevel=max` l'emporte sur le réglage de -O3 et donne O3 en
  flottants stricts. Option nouvelle : sensibilité.
* **K8, Q1 et K7 naturels** (`k8_k7.txt`, `tbaa_q1.txt`) : **exact**. `alloc::new` sans valeur initiale appelle
  `calloc` par l'interface `Allocator` ; `t_build` appelle `.dyn_search` (recherche linéaire dans la table de méthodes,
  sans cache) puis l'allocateur par un appel indirect. L'IR de C3 n'a aucune métadonnée `!tbaa` (1 190 dans l'IR de la
  référence C) ; la boucle de Q1 naturel relit les sept pointeurs de colonnes de `Cols` à chaque ligne. `HashMap` est
  chaînée et alloue une `Entry` par insertion.
* **K8, queues** : **exact**. p99,9 de 277 µs, le plus long des langages classés sans ramasse-miettes (Chapel 248,
  Odin 209) ; maximum 2,22 ms, au niveau d'Odin (2,18) et de Mojo (2,05).
* **Rejeu des errata de la remarque** (sans mesure) : exact. Errata (C4, E2, E5, F4 v1) : 70,7 points, contrôle 74,2,
  rang espéré 6,09, 5e, Zig devant dans 65 %, devant Nim dans 55 % ; avec D3 et D4 : 71,8 points, 77,2, 5,37, 5e, Zig
  devant dans 59 %. Avec les errata retenus ici (les quatre, plus D4) : 71,2 points, 75,7, 5,74, 5e. Dans ces calculs,
  Rust et Nim, à égalité au publié (6,55 et 6,57), échangent leurs places.

## 3. Plan (poussé avant les mesures)

### 3.1 Règle commune

> « Les errata de faits (la grille) et les erreurs de mon implémentation entrent dans le classement publié ; une
> optimisation nouvelle reste une analyse de sensibilité. Est une erreur : un code qui ne fait pas ce qu'il annonce
> (Ada) ou qui s'écarte d'une convention que les autres implémentations suivent (ici, des noyaux isolés de la boucle de
> mesure). Une meilleure forme ou une meilleure disposition, même plus proche de ce que fait C, est une optimisation
> nouvelle ; de même pour les options réservées aux noyaux tuned appliquées au code naturel. » (`docs/FORTRAN.md`, 3.1)

### 3.2 Ce qui entre dans le classement publié

* **Errata de la matrice de C3** : C4 = 0,5, E2 = 0,5, E5 = 0,5 et D4 = 0,5 (règles v1 et v2) ; F4 = 1 en règle v1
  (v2 inchangée). Textes corrigés : C2, C4, D4, E2, E5, E6, E7, F1 et F4. `docs/CAPABILITIES.md` régénéré ; sorties
  publiées recalculées (analyse v3, mêmes graines).
* **Aucune erreur d'implémentation** : les trois pistes mesurées sont des formes ou des options nouvelles. Rien de la
  campagne n'entre dans le classement publié ; `results/transfers.json` ne change pas.
* **README** : les trois phrases (réassociation : le contrôle local manque ; génériques par déclaration ; queue de K8)
  et la cause des écarts du code naturel (K8, Q1, K7) dans le paragraphe de C3 ; ligne du tableau si elle change.

### 3.3 Sensibilités (hors classement publié)

Toutes partent du classement publié avec les errata de 3.2.

* **S-D3** : D3 = 0,5 (règles v1 et v2).
* **S-K5** : K5 tuned avec la réduction en arbre (`c3_k5` / `c3_ref`).
* **S-thr** : K9 mt avec `posix::pthread_create` (`c3_thr` / `c3_ref`).
* **S-al** : K9 tuned et mt avec accès alignés (`c3_al` / `c3_ref`).
* **S-max** : `--optlevel=max` sur toutes les mesures de C3 du score (`c3_max` / `c3_ref`, rapport de chaque clé) ;
  les queues de latence de K8 (D3) ne changent pas.
* **S-K5+thr** : S-K5 et S-thr ensemble (la mesure de l'hypothèse « K5 et K9 mt au niveau du C » de la remarque).
* Chaque fois : score ponctuel, piliers, rang espéré, place, voisins et part des variantes où C3 les devance.

### 3.4 Mesures (`tools/measure_c3.py`, machine 13)

* `c3_ref` (source de la campagne recompilé sur l'hôte, -O3) et `c3_max` : les 27 mesures de C3 qui entrent dans le
  score (K1 naturel, mélangé, AoS et SoA ; K2 aux trois tailles ; K3 ; K4 ; K5 ; K6 ; K7 ; K8 dont `tuned_alloc` ;
  K9). `c3_k5` : K5 tuned. `c3_thr` : K9 mt. `c3_al` : K9 tuned et mt. `c` (binaire de la campagne) : K5 tuned, K9
  tuned et K9 mt, témoin des ponts.
* 61 cellules, 7 processus chacune en 7 passes ; dans chaque passe, ordre tiré au hasard (graine 20261801) ;
  répétitions de `results/calib.json`, échauffements des données principales (2 pour K5, 1 sinon) ; règle de vol du
  pilote. Sommes de contrôle validées avant la campagne. Rien d'autre ne tourne pendant les mesures.

### 3.5 Analyse (`analysis/c3_check.py`)

* Rapports appariés (moyenne géométrique des médianes de processus, intervalle par bootstrap), reportés sur les données
  principales de C3. Pour les clés témoins (K5 tuned, K9 tuned, K9 mt), règle du pont de `analysis/transfer_check.py` :
  si transfert et pont par le témoin C du même hôte diffèrent de plus de 25 %, le pont l'emporte ; sinon le transfert.
  S-max : transfert seul (pas de témoin pour chaque clé).
* Information : rapports `c3_ref` / `c` sur les clés témoins, comparés aux données principales.
* Sorties : `results/c3_check.json`, `results/report_c3.md`.
